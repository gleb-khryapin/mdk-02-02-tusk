# Этап 1. Учебная задача: система бронирования переговорных комнат

Исходная версия сервиса, намеренно написанная без соблюдения стандартов
промышленной разработки. Используется как материал для следующего этапа,
где внедряется система отладочных классов и ищется скрытая ошибка.

## Запуск

```
python app.py          # сервер на 127.0.0.1:8080
python stress.py       # 10 клиентов одновременно бронируют одну комнату
```

## Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/health` | состояние сервиса |
| GET | `/rooms` | список переговорных |
| GET | `/rooms/{id}/slots?day=` | свободные часы на дату |
| GET | `/bookings?room=&day=` | список броней с фильтрами |
| POST | `/bookings` | создать бронь |
| DELETE | `/bookings/{id}` | отменить бронь |

## Намеренные недостатки кода

- логирования нет, вся отладка через `print()`, вывод не имеет уровней,
  времени, идентификатора запроса и номера потока;
- магические числа прямо в коде: лимит `5`, границы часов `9` и `18`,
  порт `8080`, задержки `0.002`;
- захардкоженные строки: названия комнат, даты по умолчанию, тексты ошибок;
- проверка квоты и запись брони выполняются как две независимые операции.

## Скрытая ошибка

В `create_booking()` сначала считается количество активных броней,
затем выполняется запись:

```python
cnt = ...            # шаг 1: чтение
if cnt < 5:          # шаг 2: проверка
    bookings.append(booking)   # шаг 3: запись
```

Между шагами нет взаимного исключения. При последовательных запросах
квота соблюдается (шестой запрос получает 409), но при одновременной
нагрузке все потоки читают одно и то же значение счётчика и проходят
проверку.

Результат `stress.py`:

```
клиентов:             10
ответов 201 Created:  10
ответов 409 Conflict: 0
активных броней в БД: 10
лимит по условию:     5
КВОТА НАРУШЕНА: записано больше лимита
```

Ошибка воспроизводится только под нагрузкой, поэтому обычным тестированием
вручную она не обнаруживается. Её локализация с помощью журналов уровня
DEBUG выполнена на следующем этапе (корень репозитория).
